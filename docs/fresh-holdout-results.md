# A fresh, never-touched DSPy holdout — closing the repeated-touch caveat

Every prior run of `eval/run_comparison.py` and `eval/run_gepa.py` scored the
same 16-example test slice of `eval/labeled_claims.jsonl` — the pooled F1
delta, the noise-floor check, the stratified breakdown, GEPA's result, all of
it. By this project's own discipline (see README's Pillar 2 section), that
meant every number was better read as "the best estimate from a set we've
looked at many times" than a clean holdout result. This closes that gap
directly: a genuinely new test set, hand-labeled from companies that appear
nowhere in the training data, scored for the first time by this run.

## How the fresh set was built

`eval/labeled_claims.jsonl` is MSFT and NVDA only (33 + 14 + 17 + 14 records
by ticker/form). [`eval/labeled_claims_fresh_holdout.jsonl`](../eval/labeled_claims_fresh_holdout.jsonl)
uses **AMZN and AAPL** instead — two companies that have never been scored by
any extractor, optimizer, or metric in this project. 25 examples / 59 claims,
pulled from each company's real, live FY2025/FY2026 10-K MD&A text via
`RealRetrievalAgent` (no LLM call involved in retrieval), then hand-labeled by
reading the actual filing prose directly — not generated by the extraction
code under test, keeping the ground truth independent of what it's measuring,
same discipline as the original 78-example set.

Every claim's `quote` field was verified to appear verbatim in the real chunk
text before the file was written (a build-time assertion, not a manual
spot-check) — the source text uses non-breaking spaces around dates
(`December 31`) that a hand-typed quote can silently miss; catching that
class of error programmatically was cheaper than trusting a visual read.

One real finding from the labeling process itself, not a result but worth
naming: GOOGL was tried first and abandoned — its entire MD&A section
contains **zero** dollar or percent figures in the parsed prose; every number
lives in HTML tables the chunker doesn't capture as inline text. This
independently explains Phase 6's finding that GOOGL returned 0 extractable
claims in the live integration run — not a budget artifact, a genuine
absence of prose-level numbers in that filing's MD&A style. AAPL has the same
table-heavy pattern in its early sections (segment/category net sales),
which is why its 10 fresh examples come from its liquidity/contractual-
obligations section instead, where real dollar figures do appear inline.

Training still uses the full original 78-example set to bootstrap
`BootstrapFewShot`'s demos — reusing training data was never the concern,
only repeated *evaluation* against the same test set was.

## Results

| Extractor | Fresh holdout F1 (n=25, AMZN/AAPL) | Original test F1 (n=16, MSFT/NVDA) |
|---|---|---|
| Hand-written baseline prompt | **0.344** | 0.730 |
| DSPy zero-shot (`ChainOfThought`, no demos) | **0.752** | 0.784 |
| DSPy optimized (`BootstrapFewShot`, 4 demos) | **0.698** | 0.784 |

```
baseline:       precision=0.319  recall=0.373  f1=0.344  (tp=22 fp=47 fn=37)
dspy_zero_shot: precision=0.712  recall=0.797  f1=0.752  (tp=47 fp=19 fn=12)
dspy_optimized: precision=0.657  recall=0.746  f1=0.698  (tp=44 fp=23 fn=15)
```

## Finding 1 — the baseline prompt's generalization gap is real, and now resolved

The hand-written baseline prompt collapsed on genuinely new companies: 0.730
F1 → **0.344**, driven almost entirely by the `absolute` category (0.328 F1,
44 false positives across just 25 paragraphs). It looks tuned to MSFT/NVDA's
exact phrasing conventions in a way that doesn't transfer — AMZN and AAPL's
MD&A prose leans heavily on "$X billion and $Y billion in 2024 and 2025"
constructions the baseline evidently doesn't parse well.

The reasoning-based zero-shot extractor (`ChainOfThought`) held up far
better: 0.784 → 0.752, a small, expected dip from evaluating on genuinely
unseen material rather than a generalization failure.

**This time the delta survives the noise-floor check.** DSPy (either
zero-shot or optimized) vs. the hand-written baseline: **+0.355 F1** at
n=82 claim-level decisions, where the noise floor is ±0.099. The delta
*exceeds* the noise floor — a real, resolved result, not the perpetual
"inside the noise floor, inconclusive" verdict every prior run on the
repeatedly-touched test set produced. Reasoning-based extraction beating a
hand-written prompt is no longer just plausible; it's now measured on data
neither extractor had any way to have been tuned against.

## Finding 2 — a regression the old test set could never have shown

`BootstrapFewShot` didn't just fail to help here — it measurably *hurt*:
zero-shot 0.752 → optimized 0.698, a −0.054 drop. That's the opposite of the
original test set's result, where optimization produced *exactly identical*
pooled numbers to zero-shot (a wash, not a regression).

Checked against its own noise floor before treating this as a finding: at
n≈78–82 for either side of the comparison, the half-width is ±0.096–0.099.
The −0.054 drop sits *inside* that — not statistically provable at this
sample size. But it's directionally consistent with a real mechanism: the 4
bootstrapped demos were drawn from MSFT/NVDA examples, and few-shot
demonstrations are exactly the kind of thing that can overfit a model toward
a specific company's phrasing conventions rather than the task in general.
Flagged as a real, plausible regression worth further investigation with a
larger fresh set — not asserted as proven, and not smoothed into "no change"
either.

## What this changes, and what it doesn't

- **Closed:** the "same test set scored too many times" caveat that's
  followed every Pillar 2 result since `eval/run_comparison.py` was first
  built. This run is the first and only time `eval/labeled_claims_fresh_holdout.jsonl`
  has been scored by anything.
- **Resolved for the first time:** DSPy beats the hand-written baseline —
  previously stuck "inside the noise floor" on every measurement, now a real,
  noise-floor-clearing result on genuinely unseen data.
- **Newly opened, not closed:** whether `BootstrapFewShot` actively hurts
  generalization is now a live, evidence-backed question rather than a
  "roughly a wash" assumption — the fresh set is too small (n=25) to settle
  it on its own. A larger fresh holdout, or repeating this same experiment
  with a different pair of unseen companies, is what it would take to resolve
  it either way.
- **Not touched:** `eval/labeled_claims.jsonl` and its existing train/test
  split are unchanged. The fresh set is a separate file, evaluated by a
  separate script (`eval/run_fresh_holdout.py`) — nothing about the original
  dataset's role in training or the original reported numbers changes.

## Reproducing

```bash
python -m eval.run_fresh_holdout
```

Requires a reachable `LLM_BASE_URL` (see `.env`) — not part of the offline
test suite. The fresh holdout file itself was built once via
[`eval/build_fresh_holdout.py`](../eval/build_fresh_holdout.py) against live
EDGAR data (see its module docstring and the `AMZN_LABELS`/`AAPL_LABELS`
dicts for the exact chunk selections and hand-labeled ground truth); the
committed `eval/labeled_claims_fresh_holdout.jsonl` is the source of truth
and does not need to be regenerated to re-run this evaluation — re-running
the builder would pull whatever 10-K is *currently* live on EDGAR, not the
one this was labeled against.
