# Specificity check: does the pipeline cry wolf on clean filings?

[`docs/backtest-results.md`](backtest-results.md) only tests sensitivity — it shows the reconciler flags claims that turned out to be wrong, on companies that actually restated. It never checked the other direction: run against companies that *didn't* restate, does the pipeline stay quiet on genuinely accurate claims, or does it produce false positives?

[`research/specificity_check.py`](../research/specificity_check.py). Runs the real Coordinator (no mocks — real EDGAR retrieval, real LLM extraction, real Reconciler verification, the same machinery as [`phase6/run_integration.py`](../phase6/run_integration.py)) against a control set of large companies confirmed — not assumed — to carry no restatement fingerprint anywhere in Phase A's full scan (13,827 fingerprints across 541 companies).

## Finding the right control set took two attempts

The first control set (JPM, JNJ, V, COST, HD, PG, KO, MA — financials and consumer staples) produced **zero resolved verdicts**: 5 of 8 tickers had no MD&A the parser could find at all, and the other 3 spent their whole extraction budget on segment/product detail before reaching a claim the resolver covers. A real, honest finding on its own — `tools/mdna_parser.py`'s heading detection, fixed for GOOGL/AMZN's specific structure in Phase 6, doesn't generalize to bank and consumer-staples 10-Ks, which structure their MD&A very differently from the tech companies (AAPL/MSFT/NVDA) this pipeline was built against.

Switched to large tech/software names — ADBE, CRM, ORCL, CSCO, INTU, IBM, QCOM, TXN, structurally closer to the companies this pipeline's parsing and concept dictionary were tuned against — and raised the per-ticker budget (40 chunks / 40 extraction calls / 300s, up from 25/20/240). Confirmed clean the same way: none of the 8 carry a restatement fingerprint.

## What came back

126 claims across 8 tickers (all succeeded; INTU and IBM initially had no locatable MD&A within budget): **102 unverifiable, 18 consistent, 6 inconsistent.**

An apparent false-positive rate of 6/24 = 25% among resolved verdicts — a number worth investigating before reporting, not reporting at face value. It traces to two distinct root causes, only one of which is this project's own bug.

## A third real bug, found by narrowing scope: INTU's dash-separated heading

Investigating why INTU returned zero claims (rather than assuming it was the same coverage gap as the financials/consumer-staples batch) found a second, unrelated, and cleanly fixable bug. `tools/mdna_parser.py`'s heading regex only tolerated an optional *period* between an Item number and its title (`Item\s*7\.?...`) — but INTU's real FY2025 10-K heading is **`ITEM 7 - MANAGEMENT'S DISCUSSION AND ANALYSIS...`**, dash-separated with no period at all, so the regex never matched at all. Confirmed against the live filing (1,000+ lines of genuine MD&A prose sitting right after the unmatched heading) before fixing. **Fixed** by allowing an optional dash (hyphen, en dash, or em dash) as an alternative separator, with regression tests built from the real heading text. Re-verified: INTU now returns 280 real MD&A chunks (up from 0) and 11 real extracted claims (up from 0) on the next specificity run.

IBM's zero claims turned out to be a *different* thing entirely, not a bug: IBM's real 10-K literally states *"Refer to pages 6 through 38 of IBM's 2025 Annual Report to Stockholders, which are incorporated herein by reference"* — the MD&A isn't in this document at all, a real and legitimate SEC filing pattern (large filers incorporating MD&A by reference to a separate annual-report exhibit rather than repeating it in the 10-K body). Reaching that would mean fetching and parsing a second, separately-filed document — a real, different, and larger piece of work than a heading-regex fix, not attempted here. Correctly distinguishing "not present in this document" from "present but unparsed" is itself a real, if smaller, remaining gap: the parser currently returns a degenerate 1-line pseudo-section for IBM rather than raising `MdnaNotFoundError`, which happens not to affect any verdict here (0 claims either way) but is worth closing later.

With the fix, the aggregate moved to **137 claims, still 24 resolved verdicts** (INTU's 11 new claims were all unverifiable — genuine content, but segment-heavy prose that hit the extraction-call budget before reaching a claim the resolver's concept dictionary covers, the same pattern seen with JNJ and V in the first control-set attempt). The false-positive rate itself didn't move on this run, but the underlying bug fix is real and permanent — every future run against INTU, not just this one, benefits from it.

## Root cause 1: a real, previously-undiscovered resolver bug — found and fixed

The first pass of this check actually found **14** inconsistent claims (58.3% apparent false-positive rate). Investigating the largest cluster — 4 from ADBE, 3 from TXN, 1 from CSCO, all `growth_pct`/`absolute_change` claims — found a real, live bug in `resolve_periods()`'s *default* comparison-period selection (no `period_hint` present): it picked "the next most recent distinct period," by `period_end` alone, with no check that the duration matched `current`'s.

Confirmed against real TXN data: current = FY2025 revenue ($17.682B, period_end 2025-12-31). The company's own MD&A states plainly: *"Revenue of $17.68 billion increased $2.04 billion, or 13.0%, ... compared to fiscal 2024"* — an accurate claim; the real FY2024 figure is $15.641B ($17.682B − $2.04B = $15.642B, checks out). But `resolve_periods()` picked **$13.259B** as the comparison — not FY2024 at all, but a **9-month year-to-date fact from a Q3 2025 10-Q** (period_start 2025-01-01, period_end 2025-09-30). That YTD fact's period_end (2025-09-30) sorts more recently than FY2024's (2024-12-31), so the naive "closest distinct period_end" pick grabbed it instead — the exact same YTD-vs-standalone ambiguity already fixed once for the *ordinal-quarter* hint path, but never applied to the *default* (no-hint) path.

**Fixed** in [`agents/resolver.py`](../agents/resolver.py): the default comparison now prefers a distinct older period whose duration matches `current`'s (reusing the existing `_similar_length` check), falling back to the old any-distinct-period pick only when no similar-length candidate exists at all (e.g. a company with only quarterly history before its first annual figure). Regression tests added with the real TXN numbers and a fallback case. Re-running the same 8-ticker check after the fix: **14 → 6 inconsistent claims**, all 8 period-selection false positives resolved correctly.

This is exactly the value a specificity check is supposed to have: a real correctness bug, invisible to every other test in this project, because the backtest (`run_backtest.py`) builds `Claim`s directly from the fingerprint's own known period — bypassing `resolve_periods()` entirely — and every other real run happened to use companies/concepts where the default pick landed correctly by chance.

## Root cause 2, corrected: not extraction — independent per-claim period resolution

The original version of this section blamed the 6 remaining TXN/CSCO false positives on extraction picking the wrong number out of a "[current] ... compared with [prior]" sentence. That diagnosis was wrong, and worth correcting in place rather than quietly editing away: testing the actual extractor directly against the real TXN paragraphs showed it already produces the correct claims — two separate `absolute` claims, right values, right order, every time. Extraction was never the problem.

The real bug lives in [`agents/verification_agent.py`](../agents/verification_agent.py): each `ExtractedClaim` is verified **independently**. A sentence like "Net income was $5.00 billion compared with $4.80 billion." states no explicit period for either value, so both claims call `resolve_periods` with an empty hint and both resolve to the *same* most-recent fact — the $5.00B claim matches it, but the accurate $4.80B prior-year claim gets checked against the wrong (current) period and comes back "inconsistent." `resolver.py`'s own docstring already documented this exact failure class for claims that *do* state an explicit year ("fiscal years 2026 and 2025") — it just didn't cover the case where neither claim states a period at all.

**Fixed** by having [`agents/coordinator.py`](../agents/coordinator.py) number repeated `(metric, value_unit)` claims within one chunk, and passing that `occurrence` index into `verify()`: the second same-metric/same-unit absolute claim with no stated period is checked against the *comparison* fact `resolve_periods` already resolved for the first, instead of being re-resolved against current again. Keying by `value_unit` (not the claim's `quote`) mattered in practice — real TXN case: "Operating profit was $6.02 billion, or 34.1% of revenue, compared with $5.47 billion, or 34.9% of revenue." produces 4 claims for the same metric text, and the model doesn't always give paired claims an identical quote span (some come back as a truncated sub-quote), so quote-based pairing missed this case entirely.

Fixing this surfaced two more real, distinct bugs on re-verification:

- **A percent claim resolving to a dollar concept.** `"gross profit margin"`/`"total gross margin"` (added in the dictionary-narrowing round above) map to `GrossProfit` — a real XBRL concept, but one XBRL reports as a raw *dollar* figure, never a ratio. A claim like "gross profit decreased to 57.0%" then gets compared against a $10B+ fact and always "fails," which isn't a real inconsistency — no concept mapping can make that comparison meaningful. **Fixed**: a claim stating `percent` against a concept whose real unit isn't `pure` (the only XBRL representation of a ratio) now returns unverifiable instead of a guaranteed-wrong numeric comparison.
- **A bare year period hint.** "...was 12.4% in 2025 compared with 12.0% in 2024." extracts the second claim's period as literally `"2024"` — no "fiscal"/"FY" prefix — which `_FISCAL_YEAR_RE` didn't match, silently falling back to the default (most recent) period. **Fixed** with a second, tightly-anchored pattern that only matches a period hint that's *nothing but* a 4-digit year, so it can't misfire on a longer, unrelated string that happens to contain one.

## Root cause 3: a relative period hint that describes the claim's own value, not a delta

Investigating the remaining 9 (7 CRM, 2 CSCO) found two more real, distinct bugs — both period-resolution gaps, not extraction or chunking.

- **"A year ago" as an absolute claim's entire period, not a comparison reference.** Real CRM case: *"as compared to diluted net income per share of $6.36 from a year ago."* is its own standalone MD&A chunk — the current-period sentence lives in a different one, so there's no sibling claim in the same chunk for the `occurrence` fix above to pair it with. The whole claim describes the prior period on its own. `resolve_periods` already resolves the correct year-ago fact as its `comparison_fact` (its existing "a year ago"/"prior year" logic, built for delta-reference hints on `growth_pct` claims) — the fix just checks an `absolute` claim whose own period matches that same relative-year phrasing against `comparison_fact` instead of `current_fact`. Confirmed this doesn't misfire on the *legitimate* use of the same phrasing — CRM's own RPO claim ("increase of 14 percent year-over-year") is a real `growth_pct` claim where the current period genuinely is now and only the delta reference is a year ago; the fix is `absolute`-only, so that case is untouched.
- **A quarter hint with nothing to match, silently defaulting to annual data.** Real CSCO case: *"For the fourth quarter of fiscal 2025... total revenue increased by 8%."* CSCO doesn't separately tag a standalone Q4 fact (it folds Q4 into the annual 10-K, same documented pattern as the resolver's own docstring already called out) — so the claim's ordinal-quarter hint matched nothing, and `resolve_periods` fell back to the most recent (annual) fact, comparing a real ~8% quarterly growth claim against ~5.3% full-year growth and calling it a large miss. **Fixed**: a recognized quarter hint with no matching fact now raises (caught by the existing `try`/`except ValueError` → unverifiable path), matching what the docstring already said this case *should* do.

## The number that actually matters

Given the maker/checker separation this project is built around (`docs/robustness-and-scope.md`), the reconciler's own precision — given *correct* inputs — is the number worth trusting, not a blended system-level rate that conflates extraction and reconciliation errors. Re-running the full 8-ticker check after all five fixes: **137 claims, 34 resolved verdicts (28 consistent, 6 inconsistent)** — TXN's inconsistent count stayed at **0**, CSCO's Q4 claim moved from inconsistent to correctly unverifiable, and CRM's two "a year ago" claims flipped to consistent. The apparent system-level false-positive rate landed at **6/34 = 17.6%** (95% half-width ±12.8pp) — below the original 25% baseline, not just statistically tied with it.

The remaining 6 inconsistent claims (5 CRM, 1 CSCO) trace to a different class: `tools/mdna_parser.py`'s chunking splitting real sentences mid-clause, plus one genuine cross-chunk period-inheritance gap (CSCO's EPS claim) and one extraction-semantics gap (CRM misreading an FX-impact percentage as a growth claim). None of these are period-resolution bugs.

## Root cause 4: MD&A chunking splits real sentences mid-clause

Confirmed directly against CRM's live 10-K markup: a full sentence — *"For fiscal 2026, diluted net income per share was $7.80 as compared to diluted net income per share of $6.36 from a year ago."* — renders as **one `<div>` made of five sibling `<span>` elements**, each wrapping a differently-styled run (plain text, then a highlighted number, repeated). `extract_paragraphs` called `soup.get_text("\n")` on the whole document, which inserts its separator between *every* text node it walks past — including between sibling inline elements, not just real paragraph breaks. That split this one sentence into three separate downstream chunks, so extraction saw "$6.36 from a year ago" completely divorced from "diluted net income per share" and any current-period context. The same pattern split CRM's cash-flow sentence across 2 chunks and its remaining-performance-obligation sentence across 4 (the exact case behind the "$72.4 billion, an increase of 14 percent year-over-year" quote misattributed as "revenue" earlier in this doc).

**Fixed** in `extract_paragraphs`: walk *leaf* block-level elements (div/p/li/td/th/tr/h1-h6 with no such element nested inside) and join each one's own text with a plain space, instead of splitting the whole document by text node. Confirmed against the live data: all three CRM sentences above now come back as single, complete chunks with their full subject and both values intact. Regression tests added with a synthetic fixture reproducing the real sibling-span structure, plus a test confirming two genuinely separate bullet-point `<div>`s still stay separate paragraphs (the fix must not over-merge). All existing MD&A parser tests (real AAPL/MSFT/NVDA/GOOGL/AMZN/INTU fixtures) pass unchanged, and a spot-check across MSFT/NVDA/AAPL/TXN found no suspiciously oversized chunks from over-merging.

**Re-measuring is deferred, honestly.** Re-running the full 8-ticker specificity check after this fix hit two separate, real issues that make its output unusable as a clean before/after: ADBE failed entirely on a reproducible-in-sequence-but-not-in-isolation empty LLM response (`research/specificity_check.py` has no per-chunk retry, unlike `eval/run_comparison.py` — a real, pre-existing robustness gap, unrelated to this fix), and CRM's now-complete sentences exposed a *different*, previously-invisible resolver bug: several concepts resolve against the wrong period when hinted "fiscal 2026" (a Q3 fact instead of the true annual one) — invisible before only because fragmented extraction never successfully produced these claims at all. Both are real findings worth their own investigation, not something to paper over with a re-measurement that would blend three different changes into one number. The chunking fix itself stands on the evidence above (real HTML, regression tests, full existing suite green), not on a specificity delta.

## Narrowing further: what was actually in the "unverifiable" bucket

The 24 resolved verdicts above are a small fraction of the 137 real claims this control set produced — 113 came back `unverifiable`, and the same lesson that motivated the period-selection fix applied again: that bucket had never actually been inspected, just assumed to be genuinely out-of-scope (segment/product-level prose the concept dictionary was never meant to cover).

[`research/unresolved_claims_audit.py`](../research/unresolved_claims_audit.py) captures metric text, verdict, and reason code for *every* claim (not just the inconsistent ones) from the same 8-ticker control set, and tallies the unverifiable ones by metric text. Most of the 113 were confirmed genuinely out of scope on inspection — ADBE's segment ARR breakdowns, CSCO's per-geography and per-product-line revenue splits, one-off restructuring and non-GAAP reconciliation figures — the same class of "no dimensional data in the company-facts API" gap already documented above. But a real, repeated cluster wasn't: `operating profit`, `total revenue`/`total revenues`, `total gross margin`/`gross profit margin`, `diluted net income per share`, `cash provided by operations`, `common stock repurchase amount`, and `interest and debt expense` — either plain wording variants of concepts already in `METRIC_TO_CONCEPTS`, or (for `interest and debt expense`) a genuinely distinct XBRL tag, confirmed present in TXN's real company-facts data before being added.

Added all seven to the dictionary and re-ran the same 8-ticker audit: **113 → 103 unverifiable claims (24 → 34 resolved verdicts)** — a real, measured 10-claim improvement in the final, fully-fixed state (resolution rate 17.5% → 24.8%), after also correcting for every bug the expanded coverage exposed (see "Root cause 2" and "Root cause 3" above — including CSCO's Q4 claim, which correctly moved *into* the unverifiable bucket rather than staying a false positive). `total gross margin` and `gross profit margin` still show up in the post-fix unverifiable tally (2 each) — a useful negative result, and a *different* one than it first looked: the metric-text mapping resolves correctly and the claim genuinely states a percentage, but the concept it maps to (`GrossProfit`) is a dollar figure in XBRL, so these are now correctly unverifiable rather than reconciler false positives. The fix earns credit only for what it actually and correctly moved, not everything left in the bucket.

## Honest scope

8 tickers, 137 claims (after the dash-heading fix), 34 resolved verdicts in the final state — a real but small sample (95% half-width ±12.8pp on the false-positive rate), and one candidate set (financials/consumer-staples) turned up an MD&A-detection coverage gap before any specificity signal could be measured at all. The chunking/context root cause for CRM and CSCO's remaining 6 misses is a reasoned hypothesis from the visible quotes (confirmed directly for CRM's chunk-splitting, not yet for CSCO's cross-chunk period inheritance). IBM's "incorporated by reference" case remains genuinely unaddressed — a different, larger piece of work than anything fixed here.

## Reproducing

```bash
uv run python -m research.specificity_check          # ~15-20 min, real EDGAR + LLM calls, no GPU needed
uv run python -m research.unresolved_claims_audit     # same control set, full detail on every claim (not just inconsistent ones)
```
